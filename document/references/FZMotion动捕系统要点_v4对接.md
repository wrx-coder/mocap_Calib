# FZMotion 动捕系统要点 —— 对接《机器人动捕标定方案 v4》

> **定位**：从厂家文档中提取与 v4 方案、`T_torso_R` 对齐文档、静态抓取相关的信息，并逐条映射到 v4 的章节。v4 原按 OptiTrack / Motive 写成，本文给出到 FZMotion 的替换关系、由此产生的架构约束，以及需要向厂家确认的事项。
> **厂家**：北京元客视界科技有限公司（YMTE）。软件 FZMotion 3.0（Motar 版），接收 SDK 为 LuMoSDK，同步盒为 xSync（软件中称“同步精灵”，文档中也叫 SYNCER）。
> **来源**：`FZMotion3.0-Motar用户使用手册V1.0_副本.pdf`、`FZMotion导出CSV文件格式说明V1.2.pdf`、`LuMoSDK使用手册.pdf`（v1.0.0，2023-08-07）。
> ⚠️ **手册副本不完整**：37 页，只有完整目录和第 17 章（ROS 连通）、第 18 章（北极星、同步盒连接）。下文标【仅目录】的功能只能确认“有这个功能”，具体行为要查完整版手册（共 206 页）或问厂家。

## 0. 速查

```
术语替换  : Motive → FZMotion；pivot / 朝向 → “质心调整 / 刚体旋转”；刚体定义文件 → 资产文件
            NatNet → VRPN（仅刚体）或 LuMoSDK（全量）；eSync → xSync 同步精灵

数据出口  : VRPN       刚体位姿 + twist，单位 m，ROS1 vrpn_client_ros，端口 3883
            LuMoSDK    zmq + protobuf；散点 / 刚体 / 人体 + 三种时间戳；手册只提供 Windows 库
            CSV 导出   离线；刚体四元数 XYZW + 位置 mm；散点 mm；帧时间为相对录制开始的时间

架构约束  : ① 单个 marker（标定球、§1.5 特征点）走不了 VRPN → 用 CSV 散点（离线）或 LuMoSDK（在线）
            ② 外参只用静态段，按顺序配对 → 离线 CSV + ROS bag 就够，不依赖 SDK 和精确同步

纪律新增  : 刚体建好后不再动“质心调整 / 刚体旋转”；采集期间不开自校准；
            导出原始数据（不做填充 / 平滑）；资产文件与 T_torso_R 一起存档

对 v4 利好: 软件自带“探针测量”【仅目录】→ T_torso_R 方法 B 可能不用自制探针
```

## 2. 数据出口

### 2.1 三条出口对比

| | VRPN | LuMoSDK | CSV 导出 |
|---|---|---|---|
| 形态 | 在线广播 | 在线广播（zmq 收包，protobuf 反序列化） | 离线，由录制的工程导出 |
| 内容 | **只有刚体**：位姿 `/pose`、速度 `/twist`（手册中误写为 `teist`） | 帧 ID、帧时间戳、**相机同步时间戳**、**数据广播时间戳**、散点、刚体、人体、相机信息 | 刚体（位姿，可选速度 / 加速度 / 角速度 / 角加速度）、刚体资产点、散点、人体 |
| 单位 | m（ROS `PoseStamped`，`frame_id = "world"`） | 未写明 | 位置 mm；速度 m/s；角速度 rad/s |
| 姿态表示 | 四元数 | 未写明 | 四元数 XYZW（**导出时可选欧拉角，不要选**），是相对 `W` 的“全局绝对角度” |
| 时间 | `header.stamp` 为**接收端时间**（`use_server_time: False` 默认） | 三种时间戳 | 帧 ID 从 1 递增；帧时间相对录制开始；标题行有录制开始时刻 `StartTime` |
| 平台 | Linux ROS 端可用 | 手册只给 Windows 库（VS 工程、`.dll` / `.pyd`）；Python 版要求 ≥ 3.11 | 与平台无关 |
| 本项目用途 | 在线 `T_W_R`；静态抓取时的物体刚体位姿 | 在线单 marker（接球）；精确时间（δt） | **§1.5 与 MVP 外参的主数据源** |

### 2.2 VRPN 细节（手册第 17 章）

- **FZMotion 端**：在“数据传输”面板选择局域网 IP，传输对象勾选刚体，勾选 VRPN，端口默认 3883，然后开始传输。面板上还有：数据转化（示例为“原始”）、传输帧率（示例 120 Hz）、**坐标系（示例为 Y_Up）**、远程触发、UE4 格式开关。
- **Ubuntu 端**：手册只给 ROS1 路线（Ubuntu 20.04 + Noetic + `vrpn_client_ros`），用 `sample.launch` 指定服务器 IP 连接，话题为 `/vrpn_client_node/<刚体名>/pose`。示例中服务端 VRPN 版本为 07.35，客户端为 07.34，提示版本不匹配，属正常现象。
- **两个默认参数要改**：
  - `update_frequency` 默认 100 Hz，低于 FZMotion 的 120 Hz 传输帧率，会丢帧，应设为不低于传输帧率；
  - `use_server_time` 默认 False，此时时间戳里混进了网络和软件延迟及其抖动。外参只用静态数据，不受影响；δt 和在线接球则受影响，见 §3。
- **ROS2**：G1 与 `realsense-ros` 都在 ROS2 上，手册的 ROS1 路线不能直接用。可选 ROS2 的 VRPN 客户端（如 `vrpn_mocap`），或者让 agent 在 ROS2 中直接写 VRPN / LuMoSDK 接收节点。话题名和参数名都会与手册不同。

### 2.3 CSV 细节（格式说明 V1.2）

- **标题行 1**：数据名、录制帧率、录制开始时间、总帧数、长度单位（mm）、坐标系类型（示例为 World）。
- **标题行 2**：资产类型（Rigid Body / RigidBodyMarker / Marker）、名称、ID，然后是帧号、帧时间和数据列。
- **散点（Marker）**：列名形如 `Marker100242`，ID 为六位数。**同一个物理点在遮挡后重新出现时 ID 会变**（示例中同时有 100242 和 100391），所以标定球的轨迹要靠空间门限关联，不能只按 ID 取。
- **刚体资产点（RigidBodyMarker）**：列名形如 `Rigid1Marker20100`。示例中的数值在连续帧间几乎不变，**可能是由刚体位姿推算出的模板点，而不是实测点**（对应 Motive 中 Rigid Body Marker 与 Marker 的区别），未确认。因此 §1.5 的特征点和标定球**一律取散点列**。特征点 marker 不要并入躯干刚体资产，否则可能只导出模板值。
- **导出设置**（§10.6.8、§10.6.9【仅目录】）：可选导出的速度、加速度类列，标定时不需要。

### 2.4 LuMoSDK 细节

- 原理：zmq 收包，protobuf 反序列化。目录中只有 Windows x64 / x86 的动态库和静态库，示例为 VS 解决方案和 MATLAB 脚本。
- 示例程序的流程：创建接收端，设置并连接 IP，读相机信息，循环取帧数据。
- **Linux 可用性是关键未知项**：若厂家能提供 Linux 库，或 `.proto` 文件与 zmq 端口说明，Ubuntu 端即可原生接收散点和时间戳；否则需要在 Windows 侧做转发桥。见 §7 第 1 条。

## 3. 同步：xSync 同步盒

### 3.1 能力（第 12 章目录、§18.5 正文）

| 类别 | 接口 / 设置 |
|---|---|
| 输入 | 隔离输入 ISOLATED IN、通用输入 GENERAL IN、锁相输入 GENLOCK IN、时码输入 SMPTE IN、VESA IN |
| 输出 | 输出 1–3（GENERAL OUT）、隔离输出 ISOLATED OUT、锁相输出 GENLOCK OUT、时码输出 SMPTE OUT、VESA OUT |
| 输入设置 | 输入源（内部时钟 / 外部锁相等）、内部时钟频率（示例 100 Hz）、信号极性、**分频 / 倍频**、相机帧率 |
| 输出设置 | 输出类型、极性、**分频 / 倍频**、**延迟** |
| 录制触发 | 触发类型、触发源、极性（用外部信号启停录制） |
| 时码 | 时码输入源、内部时码格式、一键授时 |
| 连接 | 接到动捕 PoE 交换机，用自带适配器供电；锁到外部 Genlock 后，系统帧率跟随外部时钟（示例为 50 Hz） |

### 3.2 对 v4 §6.3「时间同步 δt」的意义

v4 的原则不变：**外参只用静态段，δt 单独标**。xSync 提供的是 δt 的硬件路线，需要时再选：

| 路线 | 做法 | 优点 | 要确认 |
|---|---|---|---|
| H1 动捕作主 | xSync 输出（分频到 D435 帧率，如 120 Hz ÷ 4 = 30 Hz）→ D435 外部同步针脚 | 帧级对应，δt 变为可测的固定偏移 | xSync 输出电平；D435 同步针脚为 1.8 V 逻辑（以 Intel 多相机同步白皮书为准），通常需要电平转换；D435 的 genlock 触发模式 |
| H2 D435 作主 | D435 主模式输出 → xSync GENERAL IN，再倍频（30 Hz × 4 = 120 Hz）→ 动捕锁相 | 不改 D435 驱动配置 | 倍频后的动捕帧率能否稳定锁定；隔离输入的电平范围 |
| H3 录制触发 | 外部信号触发 FZMotion 开始录制 | 实现简单 | 只能对齐起点，不能逐帧对齐 |
| S 软件 | LuMoSDK 时间戳 + 速度互相关（v4 原方案） | 不改硬件 | 两台主机的时钟同步（NTP / PTP） |

**建议**：MVP 阶段不碰硬件同步；δt 先走路线 S。只有当 δt 的抖动成为瓶颈（在线接球）时，再评估 H1 或 H2。

## 5. 修订后的数据链路架构

```
[FZMotion 主机 · Windows]
   ├─ 录制工程 ──导出 CSV──▶ 散点（球心 / 特征点）+ 躯干刚体 T_W_R        ← 离线主数据源
   ├─ VRPN 广播（仅刚体）──▶ Ubuntu：ROS2 VRPN 客户端 → /mocap/<刚体名>/pose
   └─ LuMoSDK 广播（散点 + 时间戳）──▶ 需 Linux 库或转发桥                 ← 在线接球 / δt 才需要

[Ubuntu · ROS2]
   └─ realsense-ros（left-IR / depth）+ VRPN 刚体 ──录进同一个 bag

[离线标定管线]
   §1.5   CSV 散点 + CSV 刚体                         → T_torso_R
   MVP    CSV（散点球心、刚体 T_W_R）+ bag（IR 检测）  → 两路各自切静止段、按顺序配对 → T_R_C, r, s
   δt     LuMoSDK 时间戳或硬件同步 + 动态数据          → δt
   静态抓取在线：VRPN（躯干刚体 + 物体刚体）→ torso 系 → MPC + IK
```

**设计要点**

1. **外参不依赖在线接口**：动捕侧完全用 CSV，相机侧用 bag。两路只需要按静止段的顺序对齐，CSV 的 `StartTime` 加相对帧时间就够了。这样可以绕开 LuMoSDK 的平台问题。
2. **只用一套坐标约定**：CSV 与 VRPN 的坐标系设置必须一致（建议都用 Z_Up）。外参在 `R` 系下求解（`p_R = (T_W_R)^{-1} · p_W`），选哪种 `W` 不影响结果；但同一批计算里混用 Y_Up 和 Z_Up 会直接出错。
3. **单位在接入层统一**：CSV 为 mm，VRPN 为 m，在解析层统一换成 m，下游不再处理单位。
4. **四元数顺序**：CSV 为 XYZW（标量在后），与 scipy 一致；Eigen 的构造函数是 WXYZ，迁移到 C++ 时注意。

## 6. 采集会话检查单（FZMotion 侧）

| 项 | 要求 |
|---|---|
| 系统标定 | 会话开始前完成并记录结果；调过镜头焦距 / 光圈后必须重做 |
| 自校准（§5.4） | **采集期间关闭**，避免中途悄悄改变相机外参；如需开启，记录开关状态 |
| 世界坐标系（§8） | 同一会话内不重设、不偏移 |
| 传输与导出坐标系 | VRPN 与 CSV 统一（建议 Z_Up）；先做手性自检：沿已知方向依次平移，检查 x × y = z |
| 数据转化 | 选“原始” |
| 数据编辑（§14） | 导出前**不做**修剪以外的处理：填充会伪造点，平滑会引入滞后（影响 δt） |
| 姿态导出 | 四元数，不用欧拉角 |
| 帧率 | 记录动捕帧率与传输帧率；ROS 端接收频率不低于传输帧率 |
| 蒙版 | 只遮 D435 发射器带来的固定假点；遮罩设置随工程存档 |
| 资产 | 躯干刚体建好后冻结；特征点 / 标定球不并入任何刚体；资产文件存档 |
| 质量记录 | 每段记录追踪质量读数；离线计算静止段 3D 抖动标准差 |
